# 编码器故障自动切换功能（同硬件等价编码器 + 透明告知 + 用户确认）

## 目标与验收标准

1. 任务因「编码器本身不可用」失败时，自动切换**同硬件家族**的等价编码器重试一次（QSV↔VAAPI 同属 Intel 媒体引擎；NVENC 无同硬件替代品则如实报错，不偷换硬件）。
2. 质量参数按等价标度换算（不是静默丢弃），被丢弃的进阶参数逐条列出告知。
3. 切换通过弹窗告知用户**为什么**（探测失败详情/运行时报错摘录），用户可选择「永久写回预设」或「仅本次任务」。
4. **不欺骗**：队列/任务详情同时展示「预设编码器」与「实际编码器」，命令行弹窗显示真实命令，任务日志留完整切换记录。

## 总体架构：三层触发，全部在服务端权威决策

```
① 启动探测（Program.cs 启动后 fire-and-forget，约2~5s，不阻塞服务）
   └─ 编码器可用性_v6.探测全部()：并行跑 6 个 1 帧探针（命令形态与 app 生成的一致：
      qsv 带 -low_power 1，vaapi 带 -vaapi_device+hwupload），结果存内存字典
② 任务启动前检查（编码任务_v6.开始Async 入口）
   └─ 若预设编码器已知不可用 → 立即切换+重建步骤（不浪费一次失败），发 WS 弹窗事件
③ 运行时兜底（编码任务_v6.开始Async 步骤循环 exitCode<>0 分支，编码队列_v6.vb:372-379）
   └─ stderr 命中编码器故障特征（MFX session/MFXVideoENCODE/Device creation failed/
      Cannot init CUDA/NVENC 初始化类）→ 切换+重建步骤+从步骤0重跑，重试仅一次
```

探测与切换函数同源（见下），②③ 走同一个 `尝试切换等价编码器()`。

## 等价映射与参数换算（新文件：`src/3fui-core/预设系统/编码器等价切换_v6.vb`）

**硬件家族**从编码器名后缀推断（与现有 `是QSV编码器` 等同款 EndsWith 风格）：
`_qsv`/`_vaapi`→Intel，`_nvenc`→NVIDIA，`_amf`→AMD。

**等价组表**（按 分类名称+家族，如 ("H.264/AVC", Intel) = [h264_qsv, h264_vaapi]；HEVC/AV1 同理）；
组内顺序即回退顺序，从用户预设所选编码器的下一个开始找「探测可用」者。

**纯函数** `切换预设到等价编码器(预设副本, 目标编码器) As 切换结果`：
返回 (新预设, 换算明细列表, 丢弃参数列表, 原因文本)。规则：

| 预设字段 | 换算规则 |
|---|---|
| 视频参数_编码器_具体编码 | 改为目标编码器名 |
| 质量控制_参数名 | `-global_quality`(QSV) ↔ `-qp`(VAAPI)；`-crf`→`-qp`；`-cq`(NVENC)↔`-global_quality`；范围同为1~51，**数值原样保留**（写明"标度一致"） |
| 比特率_控制方式 | 保留（CQP/VBR/CBR 语义通用；现有代码只给 NVENC/AMF 补 `-rc`，VAAPI/QSV 分支行为不变） |
| 编码器_编码预设 | QSV `-preset veryslow..veryfast` → VAAPI `-compression_level`：veryfast→1, faster→2, fast→3, medium→4, slow→5, slower→6, veryslow→7（反向同理） |
| 色彩管理_像素格式 | 含 "qsv" 的值→"nv12"（白名单本就会丢，这里显式改并记录） |
| 质量控制_进阶参数集 | 按目标编码器 DB 参数名（特殊/必要/默认附加列表）+ 通用白名单（-g/-bf/-refs/-threads/-aspect）过滤，**未通过的逐条记入丢弃列表**（现有行为是静默丢/崩，这里必须可见） |

## 透明度保证（对应"不能表面 QSV 实际 VAAPI"）

- TaskDto/详情/REST 三处都暴露 预设编码器 vs 实际编码器；切换记录含原因与参数变化
- 队列行徽标、弹窗、任务日志三处一致；命令行弹窗显示的是重建后的真实命令（现有步骤机制天然保证）

## 测试计划（本机实测验收）

1. `docker compose build && docker compose up -d`，`./tools/check-hw.sh` 基线通过
2. 生成测试片源：`ffmpeg -f lavfi -i testsrc2=duration=5:size=640x480 -c:v libx264 /media/probe-test.mp4`
3. 造一个 h264_qsv 预设（UI 或 API），入队转码该测试片：
   - 期望：任务启动即切换 h264_vaapi，输出成功，任务.实际编码器=h264_vaapi，切换记录含原因
   - `docker compose logs` + WS 事件（curl 不了 WS，用任务详情 REST 验证字段）确认弹窗数据源
4. 验证 libx264 预设任务**不受影响**（无探测、无切换、一次通过）
5. 验证 NVENC 预设任务正常；并验证"写回预设"路径（respond=preset 后预设文件里编码器已变）

## 风险与边界

- 探针误判（极端忙时超时）→ 单探针 20s 超时且仅影响"启动前检查"；运行时兜底仍可救
- 多阶段任务（二次编码）整步骤列表一次性重建，两遍自动同编码器（机制保证）
- AMD VAAPI 在原 NAS 的 -22 老问题：探测会标 vaapi 不可用→组内无可用者→如实报错，符合"不欺骗"原则
- 进阶参数集过滤依赖编码器 DB 参数名，DB 未收录的合法参数可能被误丢——丢弃列表可见，用户可手动补回
