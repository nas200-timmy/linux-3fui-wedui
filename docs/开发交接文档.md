## 1. 项目是什么 & 最初目标

**FFmpegFreeUI（3FUI）v6.2.26 的 Linux/Docker 网页移植版**，跑在 NAS 上做批量转码。

最初目标（开发 1 会话定调）：
- 核心逻辑（预设数据模型、ffmpeg 命令行生成、编码队列、进度解析）**直接移植**上游 VB.NET 源码，行为与 Windows 版一致（后落实为 112 项上游回归测试全绿）
- `.3fui` 预设文件与 Windows 版**双向兼容**
- UI **复刻原版操作习惯**（布局参照、非像素级模仿），"一上手仿佛网页版换皮肤的 FFmpegFreeUI"
- Docker 一键部署，NAS 浏览器直接操作
- 声明式 HTTPS（上传证书即生效）、UDP 远程调用协议与 Windows 版一致（10591 端口）

**明确不移植**（开发 1 的 MVP 边界）：ffplay 预览、AviSynth（VapourSynth 后置）、插件系统、用户统计、更新器；
VMAF 依赖 ffmpeg 构建含 libvmaf，作为可选开关。
**「像素级一致」被否**：唯一可能路线是 Wine + noVNC，但 LakeUI 依赖 D3D11 需 GPU 直通，无显卡 NAS 渲染不了，镜像还要 2GB+。

## 4. 技术栈与关键架构决策

- **核心移植而非重写**：VB.NET 直接进 `3fui-core`（net10.0 支持编译 VB），行为对上游负责；Linux 适配点收敛在 4 个 patch + 少量 `linux-3fui 适配` 注释的函数里。
- **命令行生成在核心 VB**：前端只收集预设 JSON → POST `/api/queue/tasks` → 核心生成 ffmpeg 命令。**前端任何"聪明"都不如改核心**。
- **engine 并入 core 单程序集**：原计划 core + engine 两工程，编译撞 `BC30389/BC30390`（跨程序集访问 Friend/Public 成员）与 `BC30456 '创建预设克隆工厂' is not a member of '预设管理_v6'`——根因是 **VB Module 成员跨程序集无法无前缀访问**。最终 `mv src/3fui-engine/*.vb src/3fui-core/引擎/` 合并（不是改可见性）。
- **`<InternalsVisibleTo Include="3fui-server" />`**：为了让 C# 订阅 `编码队列_v6` 的 **Friend 事件 `插件事件已触发`**（Public 的 `队列已变化`/`任务已更新` 不够用）。**删掉这行会让后端编译失败**。
- **`路径助手.数据目录` 是全局可变注入点**，替代 Windows 的 `Application.StartupPath`（服务端启动时 `路径助手.数据目录 = config.DataDir`）。目前已知至少 3 处适配依赖它：`预设存储_v6.vb:34`、未处理任务缓存路径、以及 `设置_v6` 桥接。
- **`设置_v6` 是完整桥接实现**：字段名与上游一致（`Settings.json` 互通）、原子写（`.tmp` + `File.Move` 覆盖）、`启动时加载设置()` 内含 `迁移旧设置字段`（旧布尔 `Agent权限_*` → 整数 `Agent权限级别`）。
- **暂停/恢复跨平台等价**：`引擎/Windows互操作.vb`（Windows `NtSuspendProcess/NtResumeProcess`；Linux `libc kill` SIGSTOP/SIGCONT），`编码任务_v6.vb` 两个调用点已改。
- **声明式 HTTPS 走"握手级证书选择器"**：Kestrel 常驻双端口，`ServerCertificateSelector` 每次握手从数据目录读证书（不必重启、不碰 Kestrel 手动 API）。前两版方案（独立 HostBuilder / 手动 `KestrelServer`+`SocketTransportFactory`）都因 .NET 10 API 变更被放弃。
- **Agent 用纯 HttpClient SSE 透传**，没用计划里的 `Microsoft.Agents.AI.OpenAI`；上游的 Agent 权限字段只读出来存着（早期版本没有工具调用）。
- **Agent 工具层：循环在前端、执行分两处、权限门有三处**（10-07 第三轮）。上游的工具是**直接摸 WinForms 控件**（`Agent工具封装_v6.vb` 的 `UI(Function() …)` 切 UI 线程），网页版没有 WinForms，而且**参数面板的"当前预设"只活在浏览器**（pinia + localStorage，服务端看不见）→ 所以：
  - **循环放前端**（`AgentView.vue`）：`tools` 目录由服务端下发 → 前端组装进请求 → 服务端只**透传** `tools`/`tool_choice` 给上游（`AgentProxy` 原来逐字段重建 body 会把它丢掉）→ 前端按 `index` 累加 `tool_calls` 分片 → 逐个执行 → 以 `role="tool"` + `tool_call_id` 回灌 → 最多 12 轮（上游无上限，这里加保险）。
  - **执行分两处**：`scope=server` 的 10 个工具走 `POST /api/agent/tools/{name}`（服务端直调核心 VB：队列/预设/硬件/媒体探测）；`scope=browser` 的 7 个（参数面板、准备文件）在前端执行——它们的操作对象是浏览器里的 store。
  - **三处权限门**：① 目录按 `设置_v6.Agent权限级别` 过滤后才下发（0 档 3 个 / 1 档 17 个）；② 服务端**每次调用再校验**（不足返 403，对齐上游 `Agent本地工具_v6.vb:235` 的二次判定）；③ 前端只认目录里的工具，模型幻觉调用别的名字就回灌「未授权的工具」。
  - **写操作硬确认**：上游只靠提示词要求模型先征得同意，本项目在**分发处**统一拦写类工具（服务端与浏览器工具都要），弹确认卡点「允许」才执行，拒绝则回灌「用户拒绝了该操作」。⚠ **确认必须放在分发处**（踩坑 34）。
  - 档位 2（文件系统 9 个 + `run_shell`）**本轮没移植**，所以目录里不会出现它们；`Agent权限级别` 仍显示三档但档位 2 不放行任何工具。
- **harness 通告通道（10-07 第四轮）**：软件本体要能**主动**告诉模型"现在什么情况"，而不是每轮塞一段静态快照（用户明确要求"像告警一样"）。
  - 复用 `App.vue` 那条全局 `/ws`（不新开连接），把 `event`/`task`/`progress`/`encoder-switch` 分流到新 store `useQueueFeed`（环形缓冲 200 条）；
    Agent 视图按**节流规则**消费：`event` 只在错误或关键行（开始/完成/失败/退出码…）、`task` 只在**状态变化**、`progress` 只在**进度跨 10% 档**、每任务每分钟 ≤6 条、单会话 ≤200 条。
  - 只播报"**本会话碰过的任务**"：任务 ID 由工具结果里的 32 位十六进制顺手收集（`trackTasksFrom`），没碰过的不进上下文。
  - 落成 `role:'harness'` 消息（界面是独立的 ⚙ 通知卡），发给模型时**折进首条 system 消息**的 `【harness 通知（非用户发言）】` 区块（最近 20 条 + 时间戳）。
    为什么不插入额外 system 消息：有些端点只接受单条 system；权衡是位置信息靠时间戳而不是消息顺序。
  - 通知**不自动触发新回合**（不烧 token、不突然插话），而是显示「有新通知（N）」+「让 Agent 看看」按钮；「任务播报」开关默认开、状态存 localStorage。
- **Agent 显示与健壮性（10-07 第四轮）**：
  - **思考过程**：`readStream` 除 `content` 外还收 `reasoning_content`/`reasoning`/`reasoning_text`/`thinking`，界面上默认展开的可折叠块；
    **绝不回灌上游**（DeepSeek 会因此报错），但计入 token 估算。⚠ 只回思考不回正文的一轮，以前界面是**空白**——用户看到的"卡住没下一步"就是这么来的。

## 6. 踩坑记录（新会话必读，按惨痛程度排序）

> 1~16 为原文档条目（**编号保持不变，旧引用如 §9 的"踩坑 5"仍然有效**）；17 起为 2026-10-07 汇总开发 1~4 会话追加。

1. **JS 对象数字键提升**：`options[0]` 取值时 `'15'/'48'` 被排到对象最前 → 帧率默认 15、NV FRUC 默认 48。**newPreset() 一律写 `''`，绝不取 options[0]**。（同类还有"所有『XX总开关』默认勾上"，判断写成了 `!== false`。）
2. **toast 单例**：`useToast()` 最初每次返回新实例 → toast 永远不显示。store.ts 已改模块级单例，**新增提示入口用 `useToast()` 但别自己 new**。
3. **自动命名默认空**：`输出_自动命名选项=''` → 输出文件与输入同名 → ffmpeg 原地覆盖报错。默认必须 `附加_递增时间戳`（上游枚举默认值，预设数据_v6.vb:32）。
4. **内置预设丢音轨**：7 个视频类内置预设显式写了 `音频参数_编码器_代号=""` → 覆盖默认 audio.copy → 不生成 `-map 0:a`。已补 audio.copy（`开发者内置预设_v6.vb` 现有 7 处）；**改内置预设时按视频/音频/图片三类区分**。（开发 2 提出、用户 9-29 放行、开发 3 落地。）
5. **QSV 全套诊断结论**：Debian ffmpeg 链 **libvpl 不链 libmfx**（`ldd` 验证）→ 要装 `libvpl2 + libmfx-gen1.2`（libmfx1 无用）。装齐后 `hevc_qsv` 仍报 `Invalid FrameType:0`——**Intel 核显 + libmfx-gen 25.1.4 平台级故障**（SyncOperation 返空比特流，见 qsvenc.c:2685），调参无解，别浪费时间。`h264_qsv` 必须 `-low_power 1`（核心已自动注入）；ICQ(`-global_quality`) 不支持，只有 CQP/比特率。**HEVC 硬编一律用 hevc_vaapi**。（证据链见踩坑 18/19。）
6. **编码器切换残留参数**：x265 的 `slower` 切到 VAAPI → `Error setting option compression_level` 硬报错。核心已有值列表校验兜底，前端切换编码器也有清理 watch——**新增编码器参数时检查是否走 `添加编码器参数受控`**。
7. **Integer 枚举被 checkbox 绑定**：`自动开始任务选项` 等是 Integer（0/1），checkbox 写 true 进 Integer 字段 → 保存 400。设置页已改下拉；**新增设置项先查设置_v6.vb 字段类型**。
8. **队列详情拿不到日志**：任务对象的日志缓存是私有字段，直接序列化永远空 → 前端日志对话框成摆设。Program.cs 详情端点已显式 `获取日志快照数据()` + 预设任务现场生成命令行。**新增任务相关字段时检查是否需要显式投影**。
9. **localStorage 与 v-if**：PresetView 用 v-if 时切页销毁 → 二级页/弹窗状态全丢。已改 v-show 常驻 + 二级页入 store(v4 key)。**别把它改回 v-if**。
10. **navigator.clipboard 失效**：非安全上下文（HTTP/IP 直连）不可用 → api.ts `copyToClipboard` 有 execCommand 兜底，**复制功能一律走它**。
11. **Docker 构建层缓存 / 构建快照**：构建启动后编辑源码，COPY 层可能已缓存 → 编译报"类型不存在"；**另一种是"构建已经开始"，镜像里根本没有你刚写的代码**（补 `LoginRequest`/`AuthConfigRequest` record 时连续重建两次才生效）。报错先重跑一次 build 再怀疑代码。
12. **VB 嵌套类全名**：`编码器参数列表数据` 是 `视频编码器数据库_v6` 的嵌套类，跨文件引用必须全名（踩过 BC30002；在"编码器参数值列表校验"改动里再次复现）。
13. **健康检查 401**：启用登录认证后 curl `/api/status` 返回 401 → 容器 unhealthy。compose 已改打 `/api/auth/status`（公开端点）。
14. **0 字节残骸**：失败任务留下 0 字节输出文件，用户误选当输入 → `EBML header parsing failed`。发现残骸直接删；上游有「任务失败自动删除输出」设置（默认保留）。（连锁与退出码见踩坑 21。）
15. **headless Chrome 截图坑**：虚拟时钟下"点开后才出现"的元素不做合成 → 截不到展开态。验证交互动效用 DOM 断言，别依赖截图。
16. **宿主机 sudo**：`printf '%s\n' '<你的 sudo 密码>' | sudo -S -p '' docker ...`（用户不在 docker 组）。
17. **QSV 缺的是 `libmfx-gen` 而不是 `libmfx1`**（补踩坑 5 的具体报错）：容器里 `Error creating a MFX session: -9`；`ldd /usr/bin/ffmpeg` 显示链的是 `libvpl.so.2`（Debian buildconf 是 `--disable-libmfx --enable-libvpl`）→ 装 `libvpl2 + libmfx-gen1.2`，`libmfx1` 装了也没用（Dockerfile 里留了注释）。
18. **别被"文件大小"骗了**：hevc_qsv 那次看着产出了 **38878 字节**的"成功"文件，实际那只是 3 秒音轨，视频帧全部失败（`Invalid FrameType:0`）。**判断硬编是否成功要看日志和流信息，不能只看输出存在/大小**。
19. **`Invalid FrameType:0` 的定性证据链**（补踩坑 5）：对应 FFmpeg 源码 `qsvenc.c:2685`——MFX 返回空比特流（`FrameType=0` 且 `DataLength=0`）；宿主直装 ffmpeg 同样报错、`dmesg` 无 GPU hang、`HuC: authenticated for all workloads` 正常；同现象见于 `intel/vpl-gpu-rt#353`、`jellyfin#12118`、`intel/cartwheel-ffmpeg#360` → **应用层不可修**，别再花时间调参。
20. **ffmpeg 退出码词典（实测）**：`234` = 输出容器为空（`Unable to choose an output format for ''`，上游设计如此，前端必须拦）；`8` = `No such filter: 'fruc_vulkan'`（Debian ffmpeg 563 个滤镜里我们只会用到 19 个，只缺它）；`171` = hevc_qsv 失败；`183` = 把失败留下的 0 字节残骸当输入。
21. **0 字节残骸引发连锁失败**（补踩坑 14）：任务失败（171）→ 留下 0 字节 `.mkv` → 后续任务把它当输入 → `EBML header parsing failed`（183）。看到 183 先找残骸。
22. **`X509Certificate2.NotBefore/NotAfter` 返回本地时间**：直接和 `DateTime.UtcNow` 比较，会把刚上传的自签证书判成"尚未生效"（`证书尚未生效（NotBefore 晚于当前时间）`）。统一 `.ToUniversalTime()` 再比（`TlsManager.cs:147-148` 对 NotBefore 另留 5 分钟容差，但容差不能代替时区换算）。
23. **TLS 打开后 HTTP 端口的"空响应"其实是 302**：`curl http://…` 不跟随重定向 → 看起来像服务没起来（UDP 测试第一次就是这样假失败）。调试一律打 HTTPS 端口，或加 `-L`。
24. **WebSocket 恒 400**：`context.WebSockets.IsWebSocketRequest` 永远是 false → 忘了 `app.UseWebSockets()`。
25. **`pkill -f 3fui-server` 会把自己一起杀**：shell 的命令行里就含这个关键字，`pkill` 连自己的 bash 一起杀（后台任务报"重建并重启失败"）。先 `pgrep -af` 看 PID 再杀。
26. **静态资源 404**：`Path.Combine(AppContext.BaseDirectory, "wwwroot")` 指向 `bin/`（vite 产物在项目目录）→ 用 `app.Environment.WebRootPath`。
27. **容错枚举会静默吞掉写错的枚举名**：`LenientEnumJsonConverter` 遇未知值**回退默认且不报错**。实测踩过：e2e 脚本里写 `'剪辑区间_方法': '指定时间区间'`，而 `Enum 剪辑方法`（`预设数据_v6.vb:389-397`）只有 未知/粗剪/精剪从头解码/精剪空降解码/Trim滤镜/掐头去尾/剔除中间 → 该值被回退成"未知"，**剪辑区间根本没生效，任务也不报错**。写预设/测试脚本前先 `grep -A8 "Enum "` 确认枚举名。**用容错枚举做断言是危险的**。
28. **`.mcb-layer` 包裹层会导致整棵子树不绘制**：DOM 有、`getBoundingClientRect()`/computed style 全对、染成品红后 0 像素（对照块在 body 里正常、在 layer 里不绘制）。修法＝去掉包裹层，改两个同级 `<Teleport to="body">`（面板与浮窗各自独立）。另外"把面板当组件子元素"虽能上屏，但会被 `.preset-page` 的 `overflow:auto` 裁剪——**下拉/浮层必须 fixed/Teleport**。顺带：开发 2 第 3 轮据用户给的 `原下拉窗口参考.PNG` 实测，面板底色实为**半透明毛玻璃** `rgba(18,18,18,0.82)` + `blur(20px)`，**`UI复刻计划.md §二` 的 `#242424` 基准已失效**。
29. **差分/派生指标必须与同族指标同一取整口径**：`PerfMonitor.ReadCpu` 对总占用/内存/磁盘/网络都做了 `R1`（`Math.Round(v,1)`），唯独 perCore 数组漏了 → CPU 详情页每核显示 `2.03020202020%`。修法：服务端每核补 `R1` + 前端 `Number(v.toFixed(1))` 双保险。
30. **定时器回调里未捕获的异常会杀进程**：`PerfMonitor.Tick` 必须整包 try/catch、采样失败只写 stderr；`Monitor.TryEnter` 防采样重叠（nvidia-smi 超时则跳过本轮）。
31. **杂项兼容坑**：`URLSearchParams.size` 兼容性存疑 → 改用 `toString()` 判空；vue-tsc 不接受模板里 `a?.b` 参与运算 → 移进 computed；`输出位置` ≠ `输出目录`（后者是"额外保存输出位置"，预设另存用），且后端要求 `输出位置` 非空**且目录真实存在**才生效，否则静默落到输入同目录。
32. **`NormalizeEndpoint` 只认 `/v1` 与 `/v1beta`**（10-07 修）：端点 `…/api/paas/v4`（智谱）、`…/api/v3`（火山）会被拼成 `…/v4/v1` / `…/v3/v1` → 聊天必然 404。改为**认任意 `/vN` 后缀**（上游 `GetEndpointVersion` 同款正则）后才与 models.dev 给的 base URL 对得上。**加新厂商时先确认端点末段是不是 `v数字`。**
33. **本机出网会抖，别把"抓不下来"当成代码 bug**（10-07）：同一台机器、同一个 `https://models.dev/api.json`（5.3MB），实测出现 `16KB/s`（60s 只下 975KB）、`~2s 下完`、`>60s 超时` 三种情况；连带 `docker pull debian:trixie-slim` 也会卡在 blob 上几分钟（镜像站的 manifest 秒回、blob 走上游 CDN）。
   → 因此 `ModelsDevCatalog` 的取数策略是：**有缓存就立刻给，过期也先给再后台刷新**（25s 超时 + 失败重试一次），只有"彻底没有缓存"才阻塞等网络（最长约 50s）。改这块时别退回"每次请求都同步去拉"。
   → 排查这类问题先量时序：`curl -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} total=%{time_total}\n' -o /dev/null https://models.dev/api.json`（宿主/容器各测一次，能立刻看出是网络还是代码）。
34. **写操作的确认必须放在"分发处"，不能放在某个执行分支里**（10-07 工具化轮踩到）：确认最初写在 `runBrowserTool` 内部（浏览器侧工具），结果**服务端侧的写工具（控制队列/改任务预设/存预设）完全没弹确认卡就直接执行了**——E2E 剧本 D 里"确认卡超时没出现、但队列任务预设真的被改了"就是它。修法：在 `AgentView.executeToolCalls` 里对**所有 `tool.write === true`** 统一先 `confirmWrite`，浏览器侧执行器不再自己问。**新增工具时只需要在服务端目录里标 `write=true`，确认会自动生效。**
35. **默认设置就是"入队即自动开始"**（10-07 工具化轮踩到）：`设置_v6.自动开始任务选项 = 0` 的含义是**允许自动启动**（`Program.cs` 里 `应用自动开始任务设置(值 == 0)`）。测试时用界面接口入一个任务，立刻就跑起了真实 ffmpeg（4K 文件、还是往用户的媒体库里写）。**要在测试里入队，先把 `自动开始任务选项` 置 1**（或直接用未处理状态的工具路径），跑完再恢复；做完检查一遍媒体库里有没有残骸与残留任务。

36. **E2E 打到旧前端 bundle**（10-07 第四轮踩到，浪费了两轮 E2E）：`vue-tsc -b` 只做类型检查，**不会产出 wwwroot**！改完前端必须 `npm run build`（vue-tsc + vite）。
    而且 headless Chrome 复用同一个 profile 时**会一直用 HTTP 缓存里的旧 bundle**——现象是"我的修复明明写了，E2E 却复现旧行为"（例如错误信息还是 `[object Object]`、提示词还是旧的）。
    两个都要做：① 构建后确认 `src/3fui-server/wwwroot/assets/index-*.js` 的 hash 变了；② CDP 里 `Network.enable` + `Network.setCacheDisabled {cacheDisabled:true}`（`/tmp/agent-mock/cdp_util.py` 已封装）。
37. **悬空的 tool_call 会让上游直接 400**（10-07 第四轮）：循环是"先把 assistant 的 tool_calls 落盘、再执行工具"，所以**一旦这一轮被打断**（刷新页面 / 切走 / 停止），历史里就留下"有 tool_calls 但没有配对 tool 消息"的残缺协议；
    下次请求带上去，很多端点直接报 400（报错信息还很可能被包成 `[object Object]` 那一层）。修法：加载会话时**自愈**（补一条说明性的 tool 消息）+ 发送时兜底合成。
    ⚠ 顺带：模型把"下一步"写在 `reasoning_content` 里而我们只读 `content` 时，界面会**一片空白**，看起来就像"Agent 卡住不往下走了"——用户报的"他就没有下一步了"就是这个（见 §4 的思考过程）。


38. **`-p:Version=0.1.0.dev.1` 这种「点号分 5 段」的版本号会让 NuGet restore 静默失败**：报
    `error MSB4181: The "RestoreTask" task returned false but did not log an error`，21ms 就失败、**不带任何可读原因**，
    本地与 CI 现象完全一致（排查花了很久，最后靠"同一条命令去掉 `-p:Version` 就成功"定位）。预发布后缀要用连字符：
    `0.1.0-dev.1` ✅ / `0.1.0.dev.1` ❌（`0.1.0`、`6.2.26.1` 这类 ≤4 段也 ✅）。CI 里 meta job 生成版本号已按此写死。
39. **ASP.NET Core 的 `wwwroot` 不参与 single-file 打包**：`PublishSingleFile=true`（连
    `IncludeAllContentForSelfExtract=true`）产出的 exe 旁边仍然散着 `wwwroot/`，自解压目录里也没有它
    → 只发那个 exe 就是**一个没有界面的服务**。所以 Release 里不做"单文件二进制"；要真单文件得把前端做成嵌入资源。
40. **静态根默认跟"工作目录"走，换个目录启动就只剩"前端未构建"兜底页**（HTTP 200 + text/plain，很容易误判成正常）：
    实测 `cd /tmp && /abs/path/publish/3fui-server` 就是这样。已修：`Program.cs` 在**可执行文件同级存在 wwwroot** 时
    用 `WebApplication.CreateBuilder(new WebApplicationOptions { WebRootPath = ... })` 把静态根锚过去
    （注意：`builder.WebHost.UseWebRoot()` 在 WebApplicationBuilder 上会抛 `NotSupportedException`，
    运行时错误信息已明确要求换 API）。开发态（`dotnet run`/构建输出没有 wwwroot）仍走 staticwebassets 清单，未受影响。
41. **打包结果会继承构建机的 umask**：本机 umask 002 时 `dotnet publish` 出来的 dll/wwwroot 是 0775，
    于是 deb 里全是可执行位（本机实测 `dpkg-deb -c` 看到 `-rwxrwxr-x index.html`）。CI 里已加"规整权限"步骤
    （目录 0755 / 文件 0644 / `3fui-server` 0755），并在 deb 断言里校验 `index.html` 必须是 `-rw-r--r--`。

42. **`.gitignore` 的 `bin/` 会把 `packaging/bin/` 一起吞掉**（10-07，**只有 CI 才暴露**）：本地文件就在工作区里，
    怎么试都是好的；CI 全新 checkout 缺文件 → nfpm 报 `Matching "./packaging/bin/linux-3fui": file does not exist`。
    规律：**凡被构建/打包引用的源文件，别放在叫 `bin/`（还有 `obj/`、`dist/`、`publish/`、`certs/`）的目录里**。
    自查：`git check-ignore -v <文件>`，或 `git archive HEAD | tar -t | grep <文件>` 看"干净 checkout 里到底有没有它"。

26. **工具参数校验（10-07）**：改预设/改任务预设时，未知字段直接报错并提示用 `get_parameter_field_info` 精确查询；
    **枚举字段先校验名字再写**（写错列合法取值），避免容错枚举把错值静默回退成默认（踩坑 27）。
27. **思考过程显示（10-07 第四轮）**：`readStream` 收 `reasoning_content`/`reasoning`/`reasoning_text`/`thinking`，界面默认展开的可折叠块显示；
    **绝不回灌上游**（DeepSeek 会因此报错），但计入 token 估算；**只回思考不回正文的一轮界面也要有内容**（否则看起来像卡住）。
28. **harness 通告通道（10-07 第四轮）**：软件本体主动播报任务进展。三层保护缺一不可：
    ① **只播报本会话碰过的任务**（任务 ID 从工具结果里收集）；② **节流**（event 只要错误/关键行、task 只要状态变化、progress 只要跨 10% 档，每任务每分钟 ≤6 条、单会话 ≤200 条）；
    ③ **默认开但可关**（「任务播报」开关，关掉就不产生也不注入）。注入方式是把最近 20 条折进**首条** system 消息（不插额外 system，兼容只收单条 system 的端点）。

### 8.1 发布流水线与裸部署（2026-10-07 新增）

**一句话**：打 tag 就出货。`.github/workflows/release.yml` 在 `v*` tag 上产出三类产物并创建 Release；
`workflow_dispatch` 手动跑**只构建、不发 Release**（用来验证流水线本身）。

| 产物 | 文件名 | 关键点 |
|---|---|---|
| 容器镜像 | `ghcr.io/nas200-timmy/linux-3fui-wedui:<版本>`（tag 时另加 `:latest`） | buildx 多架构 amd64+arm64；Dockerfile 阶段 1/2 加 `--platform=$BUILDPLATFORM`，arm64 不在 QEMU 里跑 npm/dotnet，只做 `-r linux-arm64` 交叉发布 |

**打包工具是 nfpm**（`packaging/nfpm.yaml`，一次出 deb+rpm）。写这个文件踩了三个坑，别再踩：
1. `depends/recommends` 必须挂在 `overrides.deb` / `overrides.rpm` 下，而 `fields`（如 Bugs）挂在**顶层** `deb:` 下——
   放错位置直接 `yaml unmarshal error`（本地 nfpm 一跑就报，不用等 CI）。
2. nfpm **只对 `version`/`arch` 做 `${}` 环境变量展开**，`contents.src` 不展开 → publish 目录固定用仓库内 `publish/`（已 gitignore）。
3. 别给 publish 目录设统一的 `file_info.mode`——会把 `.dll`/`wwwroot/*` 也变成 0755；现在沿用源权限（`3fui-server` 0755、其余 0644）。

**CI 里自带断言**（不是"构建成功就算过"）：
- 解包 tar.gz → **换个工作目录**启动 → 断言 `/api/status` 有响应 + 首页含 `id="app"` + 首页引用的 JS 能 200

### 8.2 系统兼容性：Debian 11 / 12 / 13（2026-10-07 实测）

**结论**：glibc 系发行版 **Debian 11(bullseye) 及以上都能跑**（已实测 11 与 12）；Alpine/musl 不行（只发了 glibc RID）；

**怎么测的（这套手法以后还能用，值得记）**：本机是 Debian 13，没法直接装老系统，于是——
1. 从 `deb.debian.org` 拉 bullseye/bookworm 的 `Packages.xz`，用脚本挑出 `libc6 / libstdc++6 / libssl1.1(3) / libicu67(72) / libgcc-s1 / zlib1g` 的 deb 地址并解包到 `/tmp/d11`、`/tmp/d12`；
2. `pip install patchelf` 拿到 patchelf，对**发布产物的副本**执行 `--set-interpreter <老 loader> --set-rpath <老库目录>`

3. 带 `LD_LIBRARY_PATH=<老库目录>` 启动，然后 **从 `/proc/<pid>/maps` 取证**真的加载了老库

4. 断言 `/api/status` + SPA 首页 + JS 200；再用 `TLS_CERT_PATH/TLS_KEY_PATH` 挂一张自签证书把 **HTTPS 真握手**跑通
   （证明老 OpenSSL 能用：bullseye 1.1.1w 与 bookworm 3.0.20 都是 200）。
   注：把 `tls.crt`/`tls.key` 直接丢进 `DATA_DIR/certs/` **不会**启用 TLS（`tls.active=false`）——`TlsManager.ResolvePaths()`
   还要求同目录存在状态文件 `tls.json`（只有网页上传时才写）。想声明式启用：要么三件套都放，要么用
   `TLS_CERT_PATH`/`TLS_KEY_PATH`（本次实测就是走这条路）。

### 8.3 虚拟机部署实测（2026-10-07）：4 个坑与修法

在一台 Hyper-V 虚拟机（Debian forky/sid、4 核、虚拟显卡只有 `card0`、render GID=991）上按 README 走了一遍预构建镜像路线，
暴露的问题与修法如下（**都已修，改动只在 `tools/`，不影响镜像/deb 内容，所以不需要发新版本**）：

1. **`deploy.sh` 的 group_add 自动修复写坏 override（真 bug）**：本机 `video=44` 与受版本控制的 compose 已有值相同、
   只有 `render` 不同（991 vs 105）时，脚本把 `44 991` **都**写进 override；compose 对列表是**合并（追加）**语义，
   于是有效配置成了 `[44,105,44,991]` → `docker compose config` 直接报 `items at 0 and 2 are equal` → 整条部署中止。
   **修法**：override **只写缺失的 GID**；写完后校验"无缺失且无重复"；并且**识别 compose 渲染失败这一状态**（单独再抓一次 stderr，
   因为 `compose_json` 内部把 stderr 吞了）——如果那个坏 override 是自家标记的，就**自动重写成只补缺失项**（自愈）；
   是手写的则打印出正确的 YAML 让人改。另外还写了"缺失组为空但仍有重复项"→ 把自家 override 备份成 `.bak` 并移除的分支。
2. **`check-hw.sh` 把镜像名写死成 `linux-3fui-2:latest`**：用预构建镜像部署时该 tag 不存在，所有探针误报 FAIL，
   而且 `docker run` 会先去 `docker.io` 拉一遍（雪上加霜）。**修法**：镜像名改为 `$IMAGE` > `compose config` 里的 `image` > 默认值；
   并在开跑前 `docker image inspect` 确认本地存在，不存在就**直接说清楚**（给出 `docker compose pull` / `--build` / 换镜像源三条路）后退出，不触发任何拉取。
3. **`check-hw.sh` 的 API 探针口径不一致**：它探 `https://8443`，而证书没上传前 HTTPS 必然无响应 → 报"API 无响应"误导。
   **修法**：改探 `http://127.0.0.1:8080/api/auth/status`（与容器健康检查同口径，`-L` 跟随 TLS 跳转），
   8443 无响应只作为**提示**（"没上传证书时属正常"）。容器名也从 compose 读，不再写死。
4. **虚拟机没有渲染节点 → 硬编必然失败，但不该报成 FAIL**：只有 `card0`、无 `renderD128` 时 libva 找不到驱动。
   **修法**：脚本自动探测 `/dev/dri/renderD*`；没有时把 QSV/VAAPI 报成 **SKIP（预期不可用）**，并新增一条
   **CPU 软编探针（libx264）**证明镜像与 ffmpeg 正常——这样"硬编不可用"和"容器坏了"能一眼分开。
   另外 `--device /dev/dri` 只在 `/dev/dri` 存在时才加（否则 `docker run` 会直接报错，掩盖真实原因）。

**顺带记两条环境事实（不是仓库缺陷，但值得知道）**：
- **国内直连 ghcr.io 极慢**：实测 100–300 KB/s，424MB 镜像半小时拉不完，且**客户端超时后已下载层会被清空重来**；
  换 `ghcr.nju.edu.cn` 后 ~9MB/s、31 秒拉完。该网络下 `docker.io` 认证接口也不通 → **就地构建路线不可行**（基础镜像拉不到）。
  README 已加「网络慢 / 拉不动镜像？」一节。
- **当初开发时不觉得慢**，是因为本地构建 + 有层缓存；换到干净环境就暴露了。

**验证手法（可复用）**：这次给 `tools/` 写了个 **`docker` 桩**（`PATH` 前置一个假 docker + 假 `getent`/`curl`），
桩里的 `compose config` 会按 compose 的真实语义**合并 yml + override，并在 group_add 重复时复现同款报错**。
用它跑通了 4 个场景：①无 override → 只补 991；②手写 override 只补 991 → 识别为已覆盖、不动它；
③自家坏 override → 自愈重写；④手写坏 override → 报错并给出正确 YAML；另有 check-hw 的"缺镜像不拉取""无渲染节点 SKIP"两条。
钉住这个 bug 以后不会再回来。脚本静态检查用 `bash -n` + `shellcheck -S warning`。

## 9. 已知限制 / 遗留
